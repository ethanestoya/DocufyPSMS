## NEVER AUTO-PUSH (IMPORTANT)
NEVER commit or push without the user's explicit go-ahead. After finishing a batch and passing typecheck/build, STOP and ask "Ready to push?" — only commit+push after the user confirms. (Standing instruction from the user, 2026-09-14.)

## PUSH LOG (IMPORTANT)
Keep **PUSH_LOG.md** up to date on EVERY push. Whenever anyone (you or a collaborator) pushes to the remote, add a new entry at the BOTTOM of `PUSH_LOG.md`: a new date heading, the **Philippine time (PHT, UTC+8)** of the push, whose push it was, and a short summary of what that push did. New entries go below the previous date's entry so the log reads oldest â†’ newest. (Local-only merges are NOT logged.) **Entry FORMAT (as of 2026-09-01):** write each change as its own bullet under the heading — `- Change title: brief description of the function/UI change` (e.g. `- Fixed collapsed-sidebar hover labels: ...`). Keep bullets self-contained and readable without code — describe WHAT changed and WHY (the function or UI behavior), not code snippets. One bullet per distinct change; the first bullet always summarizes the push. **Include the `PUSH_LOG.md` entry IN THE SAME COMMIT as the changes it describes — one commit per push (no separate log-only commits), and keep entries concise but detailed on what changed. This applies to ALL collaborators.** **STYLE PREFERENCE (as of 2026-09-08):** the user wants the change log written in the simple, scannable style used for the daily "Today's Changes" PDF list — a SHORT action-first title (e.g. `Implemented Locking Mechanism`, `Simplified the down-payment tier`) followed by a brief one-line description of WHAT changed and WHY. Keep it short and easy to scan; avoid long multi-clause paragraphs and code-level detail. **INCLUDE the date (and time when known) of the changes** in the heading/entry so it is easy to see WHEN each change was made.
